# AutoBak - архитектура

## 1. Из чего состоит

| Компонент | Что это | Вес |
|---|---|---|
| `autobak-agent` | Статический Go-бинарь на сервере. **Не демон**, портов не слушает. | ~8 МБ |
| `autobak` | Оконное приложение (Wails) и командная строка в одном файле. | ~12 МБ |
| `autobak-web` | Тот же интерфейс через браузер, для выделенной машины под бэкапы. | ~13 МБ |
| `internal/uiapi` | Ядро интерфейса. Оба интерфейса - тонкие обёртки над ним. | - |
| repo | Контент-адресуемый репозиторий: локальный диск или S3. | - |

Окно и веб вызывают одни и те же методы `uiapi`. Разделять их нельзя:
два интерфейса, написанные порознь, расходятся уже через месяц, и
расходятся молча - в одном из них подтверждение перед необратимым
действием оказывается слабее, чем в другом. Отличается только то, чего в
браузере физически быть не может: диалоги выбора файла и открытие каталога
в проводнике. В вебе соответствующие поля заполняются вручную.

Ничего не устанавливается кроме одного файла на сервере + systemd-таймера.

## 2. Поток данных

```
                      ┌── S3 / B2 (push-режим, по таймеру, работает без ПК)
   сервер             │
 ┌──────────┐   dump/tar/CDC/zstd/AEAD
 │  agent   ├─────────┤
 └────┬─────┘         │
      │ SSH (stdio)   └── десктоп ──► локальный репозиторий (pull-режим)
      ▼
  ┌────────┐
  │ автобак│  (управление, каталог снимков, restore)
  └────────┘
```

Два режима, выбираются на сервер:

* **push** - `systemd timer` на сервере дёргает агент, тот пишет прямо в S3.
  Плюс: бэкапы идут, даже когда ПК выключен; трафик не проходит через домашний канал.
  Требует S3.
* **pull** - десктоп по расписанию сам заходит по SSH, тянет поток и складывает в локальный репозиторий.
  Плюс: на сервере вообще нет ключей от хранилища. Минус: работает только когда ПК включён.

Репозиторий **никогда не лежит на самом сервере** (кроме опционального кэша индекса ~несколько МБ).

## 3. Формат репозитория

```
repo/
  config.json           # id репо, параметры чанкинга, KDF-соль (не секрет)
  keys/<id>             # master key, обёрнутый Argon2id(пароль)
  data/<aa>/<hash>      # паки чанков: zstd → XChaCha20-Poly1305
  index/<id>.idx        # chunkID → (pack, offset, len)
  snapshots/<id>.json   # манифест снимка (зашифрован)
  locks/<id>
```

* **CDC** (content-defined chunking, gear-хэш, нормализация FastCDC):
  средний чанк 512 КБ, min 128 КБ, max 2 МБ. Правка одного файла на 4 ГБ
  сайте = дельта в единицы мегабайт.
  Размер подобран по измерению на стенде: мелкая правка стоит примерно один
  чанк, а не долю файла, поэтому крупный чанк губителен для файлов в
  единицы мегабайт - а именно такого размера типовой дамп базы.
* **zstd-3** до шифрования - дампы БД жмутся в 4–8 раз.
* `chunkID = HMAC-SHA256(chunkIDKey, plaintext)` - дедуп без раскрытия содержимого имени файла.
* Мелкие чанки пакуются в паки по ~16 МБ - чтобы не плодить миллион объектов в S3.

**Ключи - свои на каждый сервер.** Взлом сервера А не даёт доступ к бэкапам сервера Б.
Внутри одного сервера дедуп полный (это и даёт основную экономию).
Обоснование: сервер и так хранит свои сайты и БД в открытом виде - держать там ключ
от бэкапа *этих же* данных не ухудшает модель угроз. А вот делить ключ между серверами - ухудшает.

## 3a. Блокировки репозитория

Одновременный `prune` и бэкап - единственная комбинация, способная
разрушить репозиторий изнутри. `prune` считает живыми только те чанки, на
которые ссылаются **сохранённые** снимки; паки идущего прямо сейчас
бэкапа не видны никому, потому что его манифест ещё не записан. Без
блокировки очистка снесла бы их как мусор.

```
locks/<id>    зашифрованный файл: операция, хост, PID, момент обновления
```

* бэкап, восстановление и `verify` берут **разделяемую** блокировку;
* `prune`, пересборка индекса и смена пароля - **исключительную**;
* захват идёт по схеме «записал - огляделся»: файл создаётся, затем
  читается список всех блокировок, и при конфликте свою удаляют. Список в
  S3 может отставать, поэтому второй просмотр важнее первого;
* блокировка обновляется раз в 45 секунд и протухает за три минуты -
  упавший процесс не блокирует репозиторий навсегда;
* агент права удаления не имеет вовсе, поэтому его блокировка не
  снимается, а истекает;
* потеря lease обнаруживается: если связь с хранилищем прерывалась дольше
  срока годности, `Lock.Lost()` возвращает true, и бэкап отказывается
  сохранять снимок, а prune - удалять. Иначе за время «немого» окна другой
  процесс счёл бы репозиторий свободным, и снимок сослался бы на уже
  удалённые чанки;
* нечитаемый файл блокировки различается: заведомый мусор (не расшифровался)
  можно игнорировать и удалять, а транзиентную ошибку чтения - нет, за ней
  может стоять живая операция.

**Неизменяемость записи.** Паки, индексы, снимки и ключи пишутся режимом
«только создать» (`PutNew`: `If-None-Match: *` в S3, атомарный `link` +
`O_EXCL` локально). Имя такого объекта привязано к содержимому или уникально,
поэтому «уже есть» означает «те же байты» - повтор после сбоя сети безопасен,
а перезапись чужого объекта мусором - нет. Это закрывает ошибки нашего кода и
защищает локальный репозиторий; против захваченного сервера с сырыми ключами
от S3 нужен Object Lock на стороне хранилища (см. раздел 4).

## 4. Безопасность

1. **Нет открытых портов, нет демона.** Аутентификация - SSH-ключ.
2. Отдельный ключ в `authorized_keys` с
   `command="/usr/local/bin/autobak-agent serve --backup-only --allow=/home,/var/www",restrict`.
   Три уровня ограничения:
   * `restrict` - ни shell, ни туннелей, ни pty, только протокол агента;
   * `--backup-only` оставляет из команд лишь `discover`, `export`, `backup`,
     `version`, `selftest`. `import` пишет произвольные файлы от root, то есть
     ключ с ним равносилен root, - для бэкапов не нужна;
   * `--allow` ограничивает **данные**: план приходит от клиента в каждом
     запросе, и без серверного списка украденный ключ запросил бы выгрузку
     `/etc/shadow` или ключа репозитория. Пути плана проверяются против
     `--allow` до чтения хоть байта; базы - только с `--allow-db`. Список
     выводится из плана автоматически и вписывается в строку ключа.
   Восстановление выполняется отдельным ключом, который человек подставляет
   осознанно (`install.sh --key-restore`).
3. Права: по умолчанию отдельный юзер `autobak` + `CAP_DAC_READ_SEARCH` на бинаре
   (читать всё, писать - ничего). Root - только если явно включён restore-режим.
4. S3-ключи на сервере: `PutObject` + `ListBucket`, **без `DeleteObject`**.
   Наш код к тому же пишет неизменяемые объекты режимом «только создать»
   (раздел 3a). Но это защита от ошибок и от захваченного ДЕСКТОПА; захваченный
   СЕРВЕР в push-режиме держит сами ключи от хранилища и может обратиться к S3
   напрямую. Поэтому неизменяемость обеспечивается на стороне хранилища:
   **bucket versioning + Object Lock (WORM)** → ни стереть, ни перезаписать
   прошлые бэкапы нельзя. `prune` делает десктоп своим, полноправным ключом.
5. Ключи на ПК - в Windows DPAPI (привязка к учётке). Плюс печатаемый recovery-код:
   потеряв ПК, репозиторий открывается паролем с любой машины.
6. Пароли БД никогда не попадают в `argv` - только `--defaults-extra-file` (0600) или env.
7. Опасные действия (restore поверх боевого, prune, удаление сервера) требуют
   ввода имени объекта, а не просто «ОК».
8. `verify` - раз в месяц авто-проверка AEAD-тегов случайной выборки чанков плюс
   тестовое восстановление снимка в temp с проверкой контрольных сумм.
   Непроверенный бэкап - это не бэкап.

## 5. Коллекторы (что умеет собирать)

| Модуль | Что берёт | Как |
|---|---|---|
| `files` | произвольные пути, excludes (glob) | uid/gid/mode/mtime/symlink/ACL/xattr |
| `mysql` | MySQL / MariaDB | `mysqldump --single-transaction --routines --triggers --events`, **стрим напрямую в чанкер**, на диск сервера ничего не пишется |
| `postgres` | PostgreSQL | `pg_dump -Fc` по БД + `pg_dumpall --globals-only` |
| `docker` | тома, compose-файлы, список образов | тома через `tar` из `_data`, compose по label `com.docker.compose.project.config_files` |
| `configs` | nginx, php-fpm, apache, systemd units, crontabs, letsencrypt | |
| `hestia` | `/usr/local/hestia/{data,conf}`, шаблоны, SSL | + `v-list-*` для метаданных |

Ни один коллектор не создаёт временных файлов размером с данные - всё стримится.

## 6. Автообнаружение

`autobak-agent discover --json` возвращает карту сервера: панель, сайты (root, юзер,
PHP-версия, связанные БД), базы с размерами, docker-стеки, найденные конфиги.
Десктоп рисует дерево с чекбоксами - отмечаешь «эта БД + этот сайт + nginx + fpm»,
это сохраняется как план. Ровно один экран между «добавил сервер» и «бэкапится».

## 7. Восстановление

* Всегда сначала **dry-run**: сколько файлов, что будет перезаписано, какие БД затронуты.
* По умолчанию БД восстанавливается в `dbname_restore_YYYYMMDD`, поверх боевой - только явным выбором.
* Файлы по умолчанию в `/restore/<snapshot>/…`, поверх - только с подтверждением.
* «Развернуть на новый сервер»: ставит агент, льёт конфиги, БД, сайты, поднимает docker compose.

## 8. Retention

GFS: N последних / дневных / недельных / месячных / годовых.
`prune` считает ссылки на чанки честно и удаляет только недостижимые.

## 9. История конфигураций в git (отдельный канал)

Не хранилище бэкапов. Git плохо подходит для двоичных данных: он ничего
не забывает (удалить старое можно только переписав историю), не даёт дельт
по зашифрованным данным, а репозиторий на сотню гигабайт нельзя клонировать.

Зато git даёт то, чего снимки не дают: `git log -p` по конфигу nginx за
полгода. Поэтому в git уезжает только текстовое и мелкое - конфигурации,
шаблоны панели, compose-файлы и структура баз без данных.

Работает на десктопе, а не на сервере: доступы к git-серверу на
бэкапируемых машинах не появляются. Файлы, похожие на секреты (`.env`,
`*.key`, `*.pem`, `my.cnf`, `.pgpass`, `wp-config.php`, `settings.php`,
`/etc/ssl/private`), не выгружаются - утечка на git-сервер переживёт любую
последующую «уборку истории». Из дампов схемы БД дополнительно вырезаются
строки с паролями и хешами (`GRANT ... IDENTIFIED BY`, `CREATE ROLE ...
PASSWORD`): даже хеш подбирается офлайн, и в git ему не место.

## 10. Локальный режим

`sshx.Target{Local: true}` запускает агента прямо на этой машине, без ssh.
Нужен в двух случаях: когда autobak стоит на самом сервере, и для сквозных
тестов - они прогоняют настоящий процесс агента, а не вызывают пакеты
в обход. Всё, что тестируется в обход процесса, имеет привычку ломаться
именно в процессе.

## 11. Интеграционный стенд

`test/docker` - образ Debian с настоящими MariaDB, PostgreSQL, nginx,
php-fpm, sshd, данными HestiaCP и Docker. `test/integration.ps1` собирает
агента и тестовый бинарь кросс-компиляцией, кладёт их в образ и запускает.

Проверяется то, что нельзя проверить на Windows: дампы баз, уничтожение
и восстановление базы со сверкой строк, владельцы и xattr после restore,
работа через настоящий sshd с ключом, ограниченным `command=`, и отказ
этого ключа во всём остальном.

Стенд оправдал себя сразу: на первом же прогоне он нашёл, что MariaDB не
понимает `--set-gtid-purged=OFF` (все дампы MySQL падали), и что средний
чанк в мегабайт слишком груб для дампов в единицы мегабайт.

## 12. Дедупликация по сети

Инкрементальность в хранилище экономит место, но не канал: если агент шлёт
весь сайт целиком, а десктоп уже потом отбрасывает известное, по домашнему
каналу каждую ночь едут все четыре гигабайта.

Поэтому агент режет файлы сам. Десктоп передаёт ему в запросе:

* ключ вычисления идентификаторов чанков (один из четырёх, выведенных из
  master key через HKDF);
* параметры чанкера, включая секретный seed.

Дальше агент называет чанки теми же именами, что и десктоп, и спрашивает
пачками по 512 штук или 8 МБ, какие из них уже есть. Пачками, а не по
одному: на канале с пингом 30 мс десять тысяч файлов означали бы час
чистого ожидания.

Что при этом получает сервер и чего не получает:

* **получает** возможность проверить, есть ли в хранилище конкретное
  содержимое - но только своё собственное, которое у него и так есть;
* **не получает** возможности расшифровать хоть один чанк: данные закрыты
  другим ключом, который на сервер не попадает никогда.

Две проверки на стороне десктопа обязательны:

1. Идентификатор присланного чанка пересчитывается. Иначе взломанный
   сервер мог бы назвать своим чужой идентификатор и подменить содержимое.
2. Ответ «этот чанк уже есть» даётся только про чанки, которые присылал
   **этот же сервер**. Не про весь репозиторий: иначе агент мог бы
   сослаться на чужой чанк и получить его ближайшим восстановлением,
   то есть прочитать данные другого сервера.

Измерено через настоящий sshd: повторный бэкап без изменений - 0 байт,
после правки одного файла из двенадцати - 38 байт.

## 13. Kubernetes

Сохраняется состояние кластера, а не данные томов. Ресурсы выгружаются
пофайлово (дедупликация и читаемый diff), из манифестов вычищается всё,
что кластер переписывает сам. Секреты сохраняются по умолчанию и никогда
не уезжают в git-зеркало.

Данные PersistentVolume сознательно вне области: они требуют снимков CSI
и привилегированных подов, этим занимается Velero. Том, видимый на узле
как каталог, забирает обычный файловый модуль.

## 14. Уведомления

Два разных механизма, потому что они ловят разные отказы:

* уведомление об ошибке - когда что-то сломалось;
* сигнал «я жив» - когда не сломалось ничего, потому что ничего и не
  запускалось. Внешняя служба замечает пропажу сигнала сама.

Об удачных бэкапах по умолчанию молчим: ежедневное «всё хорошо» перестают
читать, и вместе с ним перестают замечать единственное «всё плохо».

## 15. Второе хранилище

Копирование идёт на уровне объектов, без расшифровки: ключ зеркалу не
нужен, а открывается оно тем же паролем. Значит, зеркало можно держать
там, куда вы не готовы отдать ключи.

Объекты репозитория неизменяемы, поэтому докачка сводится к сравнению
имени и размера - перечитывать содержимое незачем.

Порядок этапов: ключи и настройки → данные → индексы → снимки. Оборвись
копирование в любой момент, в зеркале окажется меньше снимков, но каждый
оставшийся будет полным. Обратный порядок дал бы снимки, ссылающиеся на
несуществующие данные, то есть ложное чувство сохранности.

Удалённое в источнике из зеркала не исчезает само. Зеркало существует
ровно на случай, когда с источником случилось плохое, и ошибочный prune
не должен распространяться на копию автоматически.

## 16. Проверка восстановлением

`Verify` отвечает на вопрос «данные целы?»: читает чанки и сверяет
подписи. `Drill` отвечает на другой - «а из них получается то же самое?».

Разница существенная. Между целыми чанками и восстановленным файлом лежит
весь путь: поиск по индексу, чтение пака, расшифровка, распаковка, склейка
и запись на диск. Любое звено может сломаться так, что подписи останутся
верными.

Проверяется выборка в пределах заданного объёма: под снимок на сотню
гигабайт нужны сотня гигабайт свободного места и часы времени. Выборка
случайная и разная каждый раз, поэтому покрытие накапливается. Сверка
идёт пересчётом: восстановленный файл режется заново, и имена чанков
сравниваются с записанными в снимке - они считались при бэкапе от
исходных данных, поэтому совпадение означает побайтовое равенство.

Запускается сама раз в месяц из расписания: проверка, которую надо не
забыть запустить руками, не запускается никогда.

## 17. Переезд на новый сервер

Порядок: конфигурации → сайты → базы → docker. Конфигурации раньше сайтов,
потому что иначе веб-серверу негде их искать; docker последним, потому что
стек не должен подняться до появления данных, которые он ожидает увидеть.

Перед началом цель осматривается тем же `discover`. Если на ней уже есть
сайты или базы, развёртывание отказывается работать без явного разрешения:
переезд поверх работающего сервера необратим.

В конце печатается список того, что программа сделать не может - DNS,
сертификаты, перезапуск служб, подъём стеков. Всегда, даже когда всё
прошло успешно: переезд не заканчивается копированием данных.

## 18. Запуск по расписанию

Три способа, по одному на ситуацию:

* `autobak-task.cmd` - задание в планировщике Windows, для режима
  «забирает этот компьютер». Права администратора не нужны, задание живёт
  в учётной записи пользователя. Файл намеренно на чистом ASCII: `.cmd`
  не умеет объявлять кодировку, консоль читает его в OEM-866, а редактор
  в UTF-8, поэтому любой не-ASCII текст будет сломан в одном из двух мест.
* `deploy/docker/` - контейнер с агентом для режима «сервер пишет сам».
  Пути внутри контейнера совпадают с путями на хосте: план написан в
  терминах хоста, и переименование означало бы промах при восстановлении.
  Цикл ожидания живёт в entrypoint, а не в агенте: на обычном сервере
  расписанием занимается systemd, и дублировать его внутри программы
  незачем - но в контейнере контейнер сам и есть демон.
* `install.sh --push` - systemd-таймер, тот же режим без docker.

## 19. Веб-интерфейс

Вариант для машины, купленной ровно ради бэкапов: развернул контейнер,
зашёл браузером, добавил серверы.

**Что общего с окном.** Всё содержательное. `cmd/autobak-web` не знает
про бэкапы ничего: он принимает `POST /api/<метод>` и вызывает метод
`uiapi` по имени через отражение. Список обработчиков писать вручную
нельзя - его однажды забудут дополнить, и в вебе не окажется того, что
есть в окне. Запрещено ровно два метода: `App` и `SetEmit`.

**События.** `GET /api/events` - поток SSE. У каждой вкладки свой буфер
на 64 события; вкладка, не успевающая читать, теряет события, а не
тормозит бэкап. Терять здесь безопасно: события это отображение хода
работы, а не сама работа. Важное дополнительно уходит в журнал процесса -
он переживает закрытую вкладку и виден в `docker logs`.

**Вход.** Пользователь один: это инструмент администратора. Учётные
записи с ролями были бы здесь видимостью разграничения - любой вошедший
всё равно может восстановить любой сервер. Пароль не хранится, из него
при старте выводится хэш Argon2id. Сессия - в куке `HttpOnly` с
`SameSite=Strict`; вместе с обязательным заголовком `X-Autobak` в API
это закрывает подделку запросов с чужого сайта. После пяти неудачных
попыток с одного адреса пауза растёт до пятнадцати минут.

**Расписание** живёт внутри процесса и вызывает ту же `app.RunDue`, что и
`autobak schedule run`. Отдельный cron рядом с контейнером был бы лишней
деталью установки там, где вся ценность в «развернул - и работает».
Первый прогон - через две минуты после старта: перезапуск контейнера не
должен вызывать бэкап, иначе цикл перезапусков превратился бы в цикл
бэкапов.

**Чего в вебе нет.** Диалогов выбора файла и открытия каталога: сервер не
может открыть окно на чужой машине. Соответствующие кнопки скрыты, пути
вводятся вручную.

**Развёртывание.** `deploy/web/` - образ и compose. Контейнер работает не
от root, состояние (настройки, ключи репозиториев, ключ SSH) лежит в
одном томе. Ключ SSH создаётся при первом запуске, публичная часть
печатается в журнал: её нужно разложить по серверам, а искать её потом в
томе неудобно. Порт публикуется только на петле - через этот интерфейс
доступно восстановление на любой подключённый сервер, то есть по сути
root на всех них.
