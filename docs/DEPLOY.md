# Развёртывание в прод

Короткий чеклист перед тем, как положиться на AutoBak. Код закрывает свою
часть, но три вещи включаются только на стороне окружения - без них часть
защиты не работает.

## Обязательно

### 1. Object Lock и версионирование на S3-бакете

Это не опция, а единственное, что держит бэкапы против **захваченного
сервера** и шифровальщика. Агент не получает права удаления, а наш код
пишет неизменяемые объекты режимом «только создать» - но сервер в
push-режиме держит сами ключи от хранилища и может обратиться к S3
напрямую, в обход autobak. Остановить это может только хранилище.

```
# S3-ключу выдайте ровно это, без DeleteObject:
#   s3:PutObject, s3:GetObject, s3:ListBucket
# На бакете включите:
#   - Versioning
#   - Object Lock (WORM) на срок не меньше глубины хранения
```

Тогда прошлые бэкапы нельзя ни стереть, ни перезаписать. `prune` выполняет
интерфейс отдельным, полноправным ключом - с вашей машины, а не с сервера.

### 2. TLS перед веб-интерфейсом

Через веб-интерфейс доступно восстановление на любой подключённый сервер -
это фактически root на всех них. Поэтому:

- поставьте обратный прокси (nginx/Caddy) с сертификатом **или** задайте
  `AUTOBAK_TLS_CERT` / `AUTOBAK_TLS_KEY`;
- при TLS на прокси добавьте `AUTOBAK_BEHIND_TLS_PROXY=1` - иначе кука
  сессии не станет `Secure`, и при навязанном `http://` её можно перехватить;
- если прокси проставляет `X-Forwarded-For`, добавьте `AUTOBAK_TRUST_PROXY=1`,
  чтобы защита от подбора пароля считала реальные адреса, а не адрес прокси;
- пароль (`AUTOBAK_PASSWORD`) - длинный и не в истории команд (через `.env`
  или секрет docker/compose);
- порт по умолчанию публикуется только на петле; наружу выставляйте
  осознанно и только за TLS.

### 3. Проверьте восстановление до аварии

«Бэкап есть» и «из бэкапа поднимается сервер» - разные утверждения.
Прогоните хотя бы раз вручную:

```sh
autobak drill <сервер>          # восстановит выборку и сверит побайтово
autobak verify <хранилище> --sample 1
```

`drill` запускается и сам раз в месяц из расписания, но первый прогон
сделайте руками и посмотрите на результат.

## Первый запуск: обкатка, а не сразу весь парк

1. Разверните интерфейс, включите Object Lock и TLS (пункты 1-2).
2. Подключите **один неважный** сервер, сделайте бэкап.
3. Прогоните `drill` из этого бэкапа - убедитесь, что данные поднимаются.
4. Посмотрите сутки: расписание отработало, уведомления приходят, сигнал
   «я жив» доходит до внешней службы.
5. Только потом раскатывайте на остальные серверы.

## Ограничения, о которых стоит знать

- **Один пишущий процесс на каталог настроек.** Окно, `schedule run` из
  планировщика и веб-сервер, работающие одновременно на одном каталоге,
  могут откатить друг другу состояние (межпроцессный лок защищает от
  торн-записи, но не от устаревшей копии в памяти). Держите одного писателя:
  либо веб-сервер со встроенным расписанием, либо планировщик - не оба.
- **MyISAM/Aria.** Дампятся «на ходу» без гарантии согласованности между
  таблицами (InnoDB - согласованно через `--single-transaction`). На
  современных схемах движок по умолчанию InnoDB.
- **База внутри docker-тома.** Копирование тома у работающего контейнера
  может дать торн-файлы данных. Включите «останавливать на время дампа»
  либо бэкапьте базу отдельным модулем `mysql`/`postgres` (в логах
  предупреждение).
- **Ключ с правом восстановления = root** на том сервере. Выдавайте его
  отдельно (`install.sh --key-restore`) и только когда восстановление
  реально нужно; для регулярных бэкапов - `--backup-only --allow=...`.

## Резервная копия самого доступа

Потеряете каталог настроек (`AUTOBAK_DATA`) - потеряете ключи от
репозиториев. Скопируйте его в надёжное место. Плюс запишите recovery-код
репозитория (его показывают один раз при создании): им репозиторий
открывается паролем с любой машины, даже если каталог настроек пропал.
